# Panzo 按需功能插件方案

状态：设计建议，尚未实现插件管理器或外部插件加载。统一工作区改造正在进行，可作为宿主基础。

## 产品目标

用户只安装和使用 Panzo，在应用内安装、启用、停用和移除需要的功能。功能共享素材、工作区和设置，不要求用户分别打开其他应用。可选功能包和模型仍需要下载，但由 Panzo 统一管理。

## 宿主与功能边界

宿主长期保留：窗口与功能标签、文档/素材标识及版本、撤销和保存机制、任务调度、文件访问与网络代理、凭据加密存储、插件管理及版本兼容检查。

建议的官方功能模块：

| 模块 | 内容 | 默认策略 |
| --- | --- | --- |
| 截图与基础图片编辑 | 区域截图、标注、裁剪、复制、保存 | 随应用启用 |
| 桌面贴图 | 置顶、透明度、分组、GIF 贴图 | 可选启用 |
| 离线 OCR | 本地识别和语言能力适配 | 按需启用；语言组件依赖 Windows |
| 多模态识图 | 文字、表格、描述、问答及服务适配 | 按需启用；用户配置自己的 API |
| 图片批处理 | 拼图、压缩、格式转换 | 按需启用 |
| 录制与视频 | 区域录制、音轨、鼠标跟随、编辑、MP4/GIF 输出 | 先作为一个功能包，减少相互依赖 |

图像/文本/视频等基础素材描述属于宿主。停用插件不删除素材；需要插件才能继续编辑的专有数据保留，并说明如何重新启用。

## 交互约束

- 图片工具、录制与视频、素材库和设置提供稳定的功能分区。插件注册具体操作和区内面板。
- 例如启用多模态插件后，图片区增加识别方式、提问和结果面板；截图依然先成为图片素材，用户显式发起识别。
- 插件提交参数描述、操作和结果，由宿主呈现统一界面。普通操作不自行创建独立顶层窗口。
- 用户主动使用的桌面贴图、截图选区及录制控制条属于受支持的窗口例外，由宿主管理生命周期。
- 设置中加入“功能管理”，显示已安装、启用、停用、运行中和需重启状态，提供应用内安装及本地插件包导入。
- API Key 由宿主按插件/服务作用域加密保存；插件不能枚举其他功能的凭据。

## 接口设计

功能清单包含稳定插件 ID、名称、版本、宿主 API 版本范围、依赖、权限、功能入口和执行类型。界面位置使用语义标识，例如 image.actions、image.inspector、video.inspector、settings.pages。

任务携带 task_id、plugin_id、document_id、input_revision 和输入快照，具有进度、取消、超时、结果与结构化错误。后台任务的归属不依赖 HWND 或当前活动标签。结果写回对应素材版本，并保留来源说明。

插件不能直接改写工程文件。编辑结果通过宿主的文档事务进入撤销、保存和恢复流程。导出任务使用输入快照，标签切换不取消任务。

## 拔插与生命周期

启用 → 注册功能 → 按需启动 → 执行任务 → 停止接收新任务 → 任务结束或确认取消 → 释放资源 → 停用。

空闲时可即时启停。正在录制、导出或识别时，提供“任务完成后停用”或明确取消操作。无法安全卸载的原生组件标为重启后生效。停用保留配置，卸载默认保留用户素材，删除配置另行明确选择。

安装及更新需要验证兼容版本、包完整性和发布者信息；先安装到临时目录，校验成功再替换，失败可回滚。依赖循环或不兼容时保留现有可用版本，并显示原因。

## 执行机制

第一步采用官方内置模块和注册表，将界面入口、设置、任务提交从具体功能实现中分离。此阶段实现可启停，但代码仍随主程序发布，不等同于任意外部插件安装或减小安装包。

第二步增加真正可安装的功能包。纯处理类插件可评估 WebAssembly Component Model；需要原生库的处理任务可使用带版本协议的后台进程。独立进程提供故障边界，本身不等于安全沙箱；第三方能力需要真正受限的运行环境和宿主授权接口。

录屏、GPU 预览、全局快捷键及桌面贴图优先使用受信任的官方原生模块，避免第一轮改造同时重写设备与渲染边界。外部插件接口避免直接暴露 Rust 类型、内部指针或 HWND。

Rust 原生 ABI 不提供稳定性保证，不能把跨版本兼容建立在直接加载普通 Rust 动态库上。[Rust 官方文档](https://doc.rust-lang.org/reference/items/external-blocks.html#abi)

Wasmtime 官方提供使用 Component Model 加载插件的应用示例，可作为后续处理插件原型的依据。[Wasmtime 插件示例](https://docs.wasmtime.dev/wasip2-plugins.html)

## 实施顺序与验收

1. 完成统一工作区的当前回归，保留既有截图、录制及识别能力。
2. 建立功能注册表、稳定 ID、公共任务协议和配置接口；在设置中实现官方模块的启用/停用及持久保存。
3. 先将离线 OCR、多模态识图和图片批处理接入注册表，验证同一素材在多功能间连续使用。
4. 增加本地插件包安装、兼容检查、资源包管理及回滚；选一个处理插件做真正独立安装试点。
5. 接口稳定后再提供第三方 SDK、签名发布和应用内插件目录。

验收必须覆盖：停用入口一致撤除；重启后状态保持；快捷键不能绕过停用；任务进行时不会被强制卸载；图片 A 的结果不会进入图片 B；插件异常保留工程与结果；卸载后素材可访问；不兼容更新不破坏可用版本；插件权限限制在执行端生效。

## 当前代码需要进一步解耦的部分

workspace.rs 已有持久工作区和任务处理，但标签、表单槽位及部分任务目标仍使用固定索引或窗口句柄；capture_menu.rs 和 image_workspace.rs 仍直接调用具体功能。后续应将这些连接点改为能力注册和稳定任务归属。当前统一工作区回归通过，只证明工作区关键交互，不代表插件生命周期或安全边界已经完成。

## 已确认的发布目标：GitHub 分发与本地安装

用户在 2026-10-08 补充：计划将 Panzo 开源到 GitHub，同时提供全功能应用和可选择下载的独立功能插件，下载后可自行添加到应用。

因此最终交付必须包含真实的独立插件包、安装器和运行时接入协议。模块启停只是迁移过程中的中间里程碑。

建议保持一个主程序实现，发布三类产物：

| 发布产物（示例名称） | 包含内容 |
| --- | --- |
| Panzo-Core-<version>-windows-x64.zip | 主程序、基础工作区与插件管理器，默认包含基础截图编辑 |
| Panzo-Full-<version>-windows-x64.zip | 同一主程序，预装该版本支持的全部官方插件 |
| panzo-vision-<version>-windows-x64.panzoplugin 等 | 单独的功能插件包，包含清单、执行组件及必要资源 |

.panzoplugin 是拟议的自定义包格式，可使用 ZIP 容器。清单包含插件 ID、插件版本、宿主 API 兼容范围、系统/架构、依赖、权限和入口。数据/模型资源可另外声明，避免重复打包。主程序检查兼容性、来源及完整性，并在专用目录安装；失败保留旧版本。安装时不执行来源不明的脚本。

本地安装流程：设置 → 功能管理 → 从文件安装 → 选择插件包 → 显示功能、版本、来源及权限 → 安装 → 在对应工作区启用。后续可以支持拖入插件包和应用内插件目录，最终复用同一个安装与校验流程。

GitHub Releases 可以挂载主程序、完整包和多个插件文件。[GitHub 官方发布说明](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

“勾选功能后自动下载”由 Panzo 安装器、应用内功能管理或自建下载页实现；第一版可以直接在 Releases 提供分类清晰的独立文件。完整包只是预装插件的分发组合，和精简版共享工程格式、配置及更新机制，无需为每一种功能组合构建主程序。

自动化发布需分别构建宿主和插件，生成兼容性索引及文件校验信息，再组装完整包。验收应覆盖：精简版安装插件后获得对应能力；完整包停用插件后行为一致；离线导入正确安装依赖或明确提示缺失项；跨架构/不兼容版本被拒绝；更新失败可恢复旧版本。

全功能包包含全部官方功能实现，在线 AI 仍由用户配置自己的服务和密钥。离线模型、Windows OCR 能力等外部依赖需要在包描述中明确是否随包提供。

当前 Cargo.toml 的 license 字段仍为 Proprietary。正式开源发布前需由项目所有者确定开源许可证、补充 LICENSE 并同步包元数据；本次设计记录不修改许可证，也不执行 GitHub 发布。
