# RE-MVP R1 首批实现：后台预览与定位正确性

日期：2026-09-05  
状态：首批代码与独立构建已交付；**R1仍在进行，未达到全部“流畅/丝滑”门槛，R2新UI尚未接入**。

## 1. 实际改动

- `media_decoder.rs`：在读取前关闭视频处理器额外帧率转换。它原本不只做颜色转换，还会按输出帧率重新生成时间戳，导致VFR录屏在顺序读取与随机定位时不一致。修复不是放宽PTS比较；随机定位探针同时比较时间戳和整帧像素。
- `decode_worker.rs`：MF创建、定位、预滚、读取及释放归后台线程；精确定位与正常播放不再在窗口消息中解码。窗口仅提交计划、接收完成通知和合成呈现。UI不再通过自我反复投递消息轮询后台任务，避免压住Paint/Timer。
- 请求最多一个执行中、一个待执行和一个完成结果；新定位取消过时精确任务。缓存按字节淘汰，每个解码工作线程64MiB，两路预览合计128MiB缓存上限；这不是整个进程总内存上限，MF、GPU、在途与显示帧另占内存。
- `preview_scheduler.rs`：持续同向移动允许呈现最近完成帧，不要求与最新鼠标位置完全相同；反转、离开手势、编辑修订均使不兼容结果失效。结果年龄限制250ms，松手仍精确定位。
- 拖动不再直接拿seek后的第一张旧关键帧冒充目标反馈，而是跳过预滚像素复制、读取到目标附近；镜头/光标与实际展示源帧同一时间求值。
- 拖动使用最长边960像素的临时解码画面；正常播放、精确定位、录制与导出仍用原有原始尺寸/预设。松手必须恢复原尺寸源帧，缓存命中也不能把低分辨率帧当最终画面。没有改写素材或降低录制规格。
- 关闭不再在UI析构中无界join；不可安全中断的MF/驱动调用留在线程自身完成后释放，每进程最多8个预览解码线程，防止反复重开累计无限挂起线程。活动任务有5秒超时反馈，但这不能抢占正在运行的驱动调用。

技术依据：高级视频处理包含帧率转换，[Microsoft属性说明](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-source-reader-enable-advanced-video-processing)；禁用转换需在开始读取前设置视频处理器属性，[MF_XVP_DISABLE_FRC](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-xvp-disable-frc)。[SetCurrentPosition](https://learn.microsoft.com/en-us/windows/win32/api/mfreadwrite/nf-mfreadwrite-imfsourcereader-setcurrentposition)本身不保证精确定位，所以仍保留有期限的预滚与严格检查。

## 3. 结果与证据边界

最终切片回归 **28/31 Pass、3/31 Fail**；脚本以失败退出，未放宽阈值。三项失败均为F02连续拖动的最大更新间隔，不是媒体报错或末帧错误。

| 项目 | R0基线 | 本次最终结果 |
|---|---:|---:|
| F01定点定位到内部播放状态，中位数 | 605.297ms | 43.951ms（三次43.733～44.007ms） |
| F02同项，中位数 | 2337.880ms | 28.992ms（三次27.966～29.878ms） |
| F01拖动最大呈现间隔，三次 | 未采集 | 136.585 / 124.328 / 123.824ms |
| F02拖动最大呈现间隔，三次 | 未采集 | **213.176 / 233.754 / 196.419ms，超过切片150ms检查线** |

两份素材均通过：首帧/中点/末尾随机定位与顺序解码整帧像素相同、末帧精确定位、镜头修剪增量提交、同进程两次重开、预览/导出未压缩Hash一致、两秒导出及120帧再解码。F01额外通过从头播放到时间轴终点。所有本轮原生窗口探针均为零媒体错误、GPU直出、合成输出CPU Readback为0；原工程关键资产Hash未变。

六次拖动均能松手收敛到原尺寸精确帧并开始播放。F02三次在约3秒内只呈现33/33/32张不同源帧，约11次/秒，仍明显低于RE-PERF-03目标；不是“只差几毫秒”就整体达标。该素材对应帧时间误差最大约19.4ms，说明目前主要缺口是连续反馈频率，而非把多秒前的关键帧误当成新画面。

定位中位数来自少量固定中点样本，并非100个随机目标或物理输入到可见首帧。F02定点启动大幅改善，不能抵消连续拖动检查失败，也不能证明所有GOP位置都同样快。

本轮增加的脚本化原生测试调用真实时间线处理函数，执行3秒正反拖动，再松手并立即发起播放。测试模式隔离额外OS鼠标消息，普通编辑器不受此隔离影响。它测试后台解码、窗口呈现与播放意图，不是物理鼠标到显示器的端到端测量。`scrub_settled`还要求原尺寸源帧，不能靠临时缩小帧通过。

保留的中间失败：[首轮](acceptance/RE-MVP/r1-20260905-125841-0f049c5f/baseline.json)有223.803ms间隔；[第二轮](acceptance/RE-MVP/r1-20260905-130318-7074862b/baseline.json)有754.703ms间隔。其后加入完成通知、对应源帧检查、确定性测试输入和临时轻量预览；不能仅凭后一次通过断言这些峰值在所有真实输入中消失，也不能把多项改动的综合结果归因于某一项。

切片脚本对最大拖动呈现间隔采用150ms严格检查线，且报告不同源帧数和源时间误差；这是局部回归检查，**不代替RE-PERF-03的F03帧编号素材、逐2秒24次/秒有效更新和100样本分位数**。旧基线的360帧来自带帧率转换的解码索引；本次F01无额外转换的索引为364帧，不能继续把360当作源文件真实帧数。
