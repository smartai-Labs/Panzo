# Panzo 播放响应修复报告

执行日期：2026-09-02（Asia/Shanghai）

## 结论

“已请求播放并短暂卡顿”是实现缺陷，不是预期交互。根因是时间线松手后的精确定位需要从 H.264 关键帧向前解码，而旧增量任务每处理 4 个样本还会额外等待下一次 16 ms Timer；定位期间播放状态又保持为 Paused，导致空格键虽已记录，界面却显示为等待。

当前修复后，增量定位批次通过专用窗口消息立即续调度，每批结束都把控制权交还 Win32 消息循环；键盘、鼠标、绘制和第二次暂停请求可以继续响应。用户按下空格或播放按钮后，传输按钮和标题立即显示“正在播放/暂停”，精确帧就绪后自动连续播放，不再出现“已请求播放”文案。

## 实现调整

- 新增 `WM_INTERACTIVE_RENDER`，替代 16 ms Timer 作为精确定位的主要推进机制；Timer 仅保留兜底调度。
- 每个消息最多解码 4 个样本，目标前样本不复制 BGRA；未完成时重新 Post 消息，避免长同步循环和固定 Timer 空档。
- 播放意图成为传输控件的有效播放态：第一次空格立即切换为可暂停，第二次空格可以取消，不再表现成按键失效。
- 增加 `preview-queued-playback-smoke`，在精确定位尚未完成时立即发出播放命令，记录从输入到实际连续播放的总延迟。
- `verify-editor-mvp.ps1` 新增 `ED-PLAYBACK-001`：播放意图必须被消费，旧录制项目的实际启动延迟必须小于 750 ms。
- 新录制文件的 H.264 GOP 从 2 秒缩短为 1 秒，降低编辑器随机定位时从最近关键帧向前解码的最坏距离；fMP4 Fragment 策略保持不变。
